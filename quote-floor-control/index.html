Requirements to configuration

Quote Floor Control

A discovery-to-configuration package for one control: stopping a financing quote from being released below its authorized rate floor. It includes the requirements, the configuration spec, the test matrix, and the user guide.

What this is and is not. The client, the object, and the numbers are simulated. No employer rules, rates, or records are used. The configuration spec is written for Salesforce and has not been deployed to an org. The Python model in this package checks the logic of the two validation rules; it does not prove how Salesforce will behave. Section 7 lists what a sandbox pass still has to confirm.

1. The problem

A simulated premium finance lender quotes a sell rate to insurance agencies. Each quote has an authorized floor rate, and a quote released below that floor loses margin on every installment. Releases happen after a manual review, and the review is the only control. The client wants the system to refuse an out-of-policy release instead of relying on a reviewer noticing.

The pattern comes from a real class of error I caught in release testing: a configuration change that would have let quotes out below the authorized floor. This page models the control that would have made that error impossible to ship quietly.

4. Configuration spec

Object and fields

Custom object Premium_Finance_Quote__c.

FieldTypeNotes
Status__cPicklistDraft, Pending Review, Released
Sell_Rate__cPercent (3 decimals)Quoted APR
Authorized_Floor_Rate__cPercent (3 decimals)Copied at creation; editable by managers only
Broker_Fee__cCurrency
Broker_Fee_Cap__cCurrencyCopied at creation
Override_Approved__cCheckboxEdit access limited to the manager profile

Validation rule QF_001: release below the floor

Error message: "Sell rate is below the authorized floor. Request override approval." A blank rate or floor returns a separate message asking for both values.

AND(
  ISPICKVAL(Status__c, "Released"),
  OR(ISNEW(), ISCHANGED(Status__c), ISCHANGED(Sell_Rate__c),
     ISCHANGED(Authorized_Floor_Rate__c)),
  OR(
    ISBLANK(Sell_Rate__c),
    ISBLANK(Authorized_Floor_Rate__c),
    AND(Sell_Rate__c < Authorized_Floor_Rate__c, NOT(Override_Approved__c))
  )
)

Validation rule QF_002: broker fee over the cap

AND(
  ISPICKVAL(Status__c, "Released"),
  OR(ISNEW(), ISCHANGED(Status__c), ISCHANGED(Broker_Fee__c),
     ISCHANGED(Broker_Fee_Cap__c)),
  Broker_Fee__c > Broker_Fee_Cap__c,
  NOT(Override_Approved__c)
)

The OR(ISNEW(), ISCHANGED(...)) wrapper is deliberate. Without it, any edit to a released quote, such as a note or a contact, would re-run the check and block unrelated work. Without ISNEW(), a record created directly as Released would skip the rule entirely, because ISCHANGED is false on insert. Tests T10, T15, and T16 cover both sides of that.

6. User guide

What changed for sales users

You can still create and edit draft quotes at any rate. The check runs when you move a quote to Released.

If the save is blocked

  • "Sell rate is below the authorized floor." Raise the rate to the floor or above, or ask your manager to approve an exception.
  • "Broker fee exceeds the cap." Lower the fee to the cap or below, or ask your manager to approve an exception.
  • "Sell rate and authorized floor are required." One of the two fields is empty. Fill it in and save again.

If you are a manager

Tick Override Approved only after you have approved the exception in the approval step. The box clears nothing else, so the quote still needs its rate and fee values.

Released quotes

Editing the rate on a released quote runs the same check again. Editing other fields does not.

7. What a sandbox pass still has to confirm

  • That ISNEW() and ISCHANGED() behave as modeled on records loaded by the data import tool and by any flow that updates quotes.
  • That the error messages appear next to the right field in the page layout and read clearly to a sales user.
  • That quotes already released below the floor do not block ordinary edits after deployment. This needs a data query before go-live, not a rule change.
  • That field-level access on Override_Approved__c matches the profiles the client actually uses.

The right next step in a real engagement is to load the object and rules into a developer sandbox and run the sixteen tests by hand through the interface, then record where the org and the model disagree.
